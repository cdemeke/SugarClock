# iOS 1.0.0 (35) — Wi-Fi identity checks and scan failures

Addresses Greptile's PR #29 findings after PR #81 was merged into its `iOS` branch: a reassigned address could receive another clock's changes, and a failed Wi-Fi scan could return old networks as successful results.

Each local-network client retains its expected clock identity. Saved-clock connections supply it before the first greeting; address-only clients pin the first verified identity and cannot later rebind to a replacement. Settings, status, scan results and schema access check identity before and after reading. Every POST, including direct saves, performs a fresh matching MAC check immediately before sending its request body. OTA admission is followed by another check before submission. Mismatch, missing/malformed identity, or an unavailable identity read prevents the mutation; identity failures discard the cached configuration and use the retryable connection path so the coordinator can rediscover the original saved clock.

The scan-results adapter now maps a nonempty HTTP scan error to `scan_failed`, matching Bluetooth. The coordinator reports failure and retains its previous successful results; the network sheet's existing error flow does not publish the failed scan's cached networks. An explicit retry can succeed without reconnecting or saving settings.

Validation: 210 Swift tests executed, three opt-in hardware tests skipped, zero failures. The initial identity and scan regressions failed before the fixes. Tests cover all mutation paths with an address reassignment, direct credential saves, missing/malformed identity, identity changes between OTA admission and submission or during readback, cached schema and repeated greeting, expected identity supplied before first use, recovery after a health check/save/settings update, preserved pending edits, and no writes or false confirmation on a replacement clock. Scan tests cover failure with cached networks and a successful retry. The simulator build and signed iPhone archive passed.

This changes the adapter's behavior without a new screen layout; existing connection, configuration and diagnostics screenshots remain representative. The identity checks use the existing web API and need no new firmware capability. TestFlight build 35 targets SugarClock's existing Internal group; processing, notes and tester availability are verified separately. Uncommitted app work in the original checkout is untouched, and no clock firmware was flashed.
